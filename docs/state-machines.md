# Workflow state machines

Status: draft for review

This file gives the transition tables for every workflow that changes a record's state. The Audit, Connected analysis, Content and Change machines use the states in 03-PRODUCTION-CONTRACTS ("Workflow states") exactly. The Anonymous report lifecycle, Prompt-panel run, Deletion request and Export authorization machines are designed here from D-002, D-004, 05-PROJECT-PLAN §10 and v1-baseline §10. Their state names are ASSUMPTIONS until reviewed.

State enums live in `schemas/common.schema.json` (`audit_state`, `connected_analysis_state`, `content_state`, `change_state`, `anonymous_access_state`, `prompt_panel_run_state`, `deletion_request_state`, `export_authorization_state`). The owning records are `Audit`, `ContentOpportunity` / `ContentBrief` / `ContentDraft`, `ChangeSet`, `Audit.anonymous_access_state`, `PromptPanelRun`, `DeletionRequest` and `ExportAuthorization`. Each stage attempt is a `JobStage` plus `Attempt` record.

## Conventions that apply to every table

**Retries and timeouts.** Every retry count and timeout value in this file is an ASSUMPTION. Calibrate them at M0B with load and cost tests, then move them into config. Retries use exponential backoff with jitter (ASSUMPTION: base 2 s, cap 60 s). A retry keeps the same idempotency key. A retry never crosses a human gate.

**Idempotency.** A transition is a compare-and-set on `(instance_id, from_state, row_version)` in Cloud SQL. The idempotency key is stored with the transition. Replaying a request with the same key returns the stored result and changes nothing. Key templates below use `<...>` for record fields.

**Writes to client sites.** Only the deterministic `connector` service writes to a client site, and only for an approved, snapshotted change set. No AI agent performs a transition that writes. A write is never retried without its idempotency key (02-DETAILED-SPECIFICATION §10).

**Audit events.** Every transition writes one event to the append-only audit log. 02-DETAILED-SPECIFICATION §17 requires this for every approval and write; this file extends it to every transition (ASSUMPTION). Events carry IDs, actor, from/to states, reason code and time. They never carry secrets, tokens, page text, prompts or personal data (01-PRODUCT-REQUIREMENTS §11). Event names are ASSUMPTIONS.

**Failure after retries.** When retries are exhausted, the task goes to a dead-letter queue and the instance follows the failure row of its table. Optional work (enrichment, connected sources, AI observations) degrades to `unavailable`; it never turns a useful audit into a failure (05-PROJECT-PLAN M4 exit: "absent optional data is not an error").

**Actors.** Runtime agents use the names in 02-DETAILED-SPECIFICATION §13: `auditor`, `visibility-tester`, `keyword-analyst`, `performance-analyst`, `planner`, `content-strategist`, `fixer`, `verifier`, `report-writer`. Deterministic services from the same section: `url_safety`, `crawler`, `rules_engine`, `scoring`, `keyword_validator`, `metrics_calculator`, `integrity_service`, `webhook_receiver`, `connector`, `cost_guard`. ASSUMPTION: these additional service names are introduced here: `orchestrator` (Cloud Workflows plus Cloud Tasks), `eligibility_service`, `report_composer`, `preview_service`, `export_policy_service`, `deletion_service`, `retention_job` (Cloud Scheduler). Human actors: `anonymous_visitor`, `registered_user`, `project_owner`, `approver`, `operator` (D-004: advanced roles arrive at M11).

**Terminal states.** A terminal state accepts no further transitions except the retention transitions listed in its table. Terminal behavior is stated under each table.

## 2. Connected analysis

States that registered, connected audits may add (03-PRODUCTION-CONTRACTS): `IMPORTING → KEYWORD_SYNC → PERFORMANCE_DIAGNOSIS → PROMPT_PANEL → PLANNING`, entered from `ENRICHING_OPTIONAL` (A11) and left for `COMPOSING`.

ASSUMPTION: the five states run in this order, and each is entered only when its module is `enabled` in the `CapabilityManifest`. When a module is not enabled, the orchestrator moves straight to the next enabled state and records `audit.stage_skipped` with the manifest reason. Anonymous audits never enter these states (enforced in `audit.schema.json`).

## 4. Change

States (03-PRODUCTION-CONTRACTS): `DRAFT → VALIDATED → PREVIEWED → AWAITING_APPROVAL → APPROVED → SNAPSHOTTING → APPLYING_CANARY → VERIFYING_CANARY → APPLYING → READ_BACK → PUBLIC_VALIDATION → VERIFIED | MISMATCH | PARTIAL | ROLLBACK_REQUESTED | ROLLED_BACK | HUMAN_REVIEW | REJECTED | EXPIRED`.

Owning record: `ChangeSet.status`. Rollout by tier (03-PRODUCTION-CONTRACTS, 02-DETAILED-SPECIFICATION §10): tier 1 canary of 1-2 pages, then batches (ASSUMPTION at most 25 pages); tier 2 page by page; tier 3 one change at a time through staging or a pull request, in a change window. For tier 2 the first page is the canary; for tier 3 the single change is the canary. The connector runs one change set per site at a time (site lock).
